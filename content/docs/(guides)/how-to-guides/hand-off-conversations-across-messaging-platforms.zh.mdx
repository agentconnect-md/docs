只有在来源端和目标端都是**你信任的消息工作区**时，才适合使用这种模式。你需要对两边环境拥有控制权或已明确批准，清楚目标端有哪些人可以看到内容，并接受其安全和数据保留规则。

<Image src={imgAddIntegration} alt="把 Agent 连接到经批准的消息平台" width={640} />

> **信任边界**：将 Agent 同时接入两个平台后，它具备在两者之间转移内容的能力，但这并不会让外部客户、合作伙伴或社区工作区变成可信环境。如果任意一方未获准接收相关信息，请改用一次性的、经过审核和脱敏的消息。

这里的*工作区*指的是 Slack 工作区、Discord 服务器、Lark / 飞书租户，或已知的 Telegram 群组和私聊，而不是 Agent 的代码工作区。

同一个 Agent 可以先在一个平台开启对话，向另一个可信工作区发送聚焦的交接消息，随后再将结果回报回来。这不是实时消息镜像：每个平台各自维护独立的线程（thread）、会话和可见范围。

发起交接时，AgentConnect 必须能识别请求者身份。发起人需要通过在 **个人资料 → 登录方式** 中关联的聊天账号被识别为组织成员，Agent 也只会将消息发送到该成员本人有权限发言的地方。在 AgentConnect Cloud 上，这意味着使用已关联的 Slack 账号从 Slack 发起交接。目前无法从 Telegram 或 Discord 交接到 Slack 或 Lark / 飞书，因为 AgentConnect 无法验证 Telegram 或 Discord 上的用户身份。详见[在其他对话中读取和发消息](/connect-automate/integrations-overview#reading-and-posting-in-other-conversations)。

## 开始之前 [#before-you-start]

你需要准备：

- 一个同时连接到两个消息平台的在线 Agent
- 两个获准交换相关信息的工作区
- 一个用于发起交接的已关联聊天账号（在 AgentConnect Cloud 上，即在 **个人资料 → 登录方式** 中关联的 Slack 账号）
- 一个你本人有权限发消息的目标对话：在你已关联账号的平台上，权限按该账号判定；在无法关联账号的平台（包括 Telegram 和 Discord）上，要求该 Agent 在目标对话中已经存在你可以在 **会话** 中打开的会话
- 一个有权在目标对话中发消息的机器人
- 明确的边界规则，界定哪些信息可以带离来源端

两端都由同一个 Agent 负责。如果需要两个不同的 Agent 分工协作，请改用 [Agent 间委派](/build-your-team/agents/multi-agent-work-modes#agent-to-agent-delegation)。

## 1. 连接两个平台 [#1-connect-both-platforms]

打开该 Agent，在 **集成** 中分别添加两个聊天平台集成。只把目标端机器人邀请或添加到需要触达的频道或群聊中。

首次交接前，先在 **集成 → 消息应用** 中核实目标工作区、服务器或租户。仅看频道名并不可靠，不同工作区里可能都有 `#incidents`。

## 2. 确认目标 [#2-confirm-the-destination]

在发送任何消息前，先让 Agent 列出它能访问的目标位置：

```text
List the incident channels you can reach through our approved internal bots.
Do not send a message yet.
```

在未关联账号的平台（例如 Telegram 或 Discord）上，Agent 只会往它已有会话且你能打开的对话里发消息；Telegram 机器人也只能列出 Agent 已经看到过的聊天。请先在目标聊天中 `@` 一次机器人。在任何平台上，机器人都必须具备在该对话中查看和发消息的权限。

## 3. 发起一次聚焦的交接 [#3-start-a-focused-handoff]

在 Slack 中明确指定可信目标，以及允许共享的具体内容：

```text
Hand this incident off to #incidents on our approved Discord server.

- Post a new top-level message.
- Include the symptoms, what I already tried, and the open question.
- Do not copy names, credentials, or unrelated messages from this DM.
- Ask the team for a decision.
- When they reply, send a concise result back here.
```

在目标频道发出一条新的顶层消息后，会创建一个关联的目标会话。团队成员可以直接在那里回复，Agent 也能把要求的结果回报回来源端。相比之下，直接发进一条无关的旧线程里会模糊交接边界。

## 4. 让规则可复用 [#4-make-the-rule-reusable]

如果跨平台交接是常见操作，可以把简短的规则写进 Agent 的 **描述** 中：

```text
When moving work between messaging platforms:
1. Use only approved workspaces.
2. Stop and ask if the destination cannot be verified.
3. Share a concise handoff, not the full source transcript.
4. Never copy secrets or private-message details without approval.
5. Keep the source and destination as separate conversations.
6. Report only the requested result back to the source.
```

## 哪些内容保持分离 [#what-stays-separate]

- **信任**：机器人能发到某个频道，不代表该工作区或其中的每个成员都已获准接收信息。
- **会话**：来源端和目标端依然是两条关联但各自独立的会话。
- **访问**：每个平台执行各自的机器人与对话权限，Agent 也只会访问和发送到请求者本人有权限的地方。
- **线程**：所有回复留在各自平台，除非 Agent 主动将结果回报回来。
- **身份**：只有当两个平台的账号都关联到同一个 AgentConnect 个人资料时，它们才会被视为同一个人。

适合交接的场景包括：在可信团队工作区之间转移内部事件、把私信问题升级到团队频道，或同步经过审核的结论摘要。不要跨不同信任级别做常规交接，也不要搭建自动双向镜像——这会带来重复消息、责任不清以及信息泄露风险。

连接平台见[集成概览](/connect-automate/integrations-overview)，查看两端会话记录见[会话](/operate-govern/sessions)。
