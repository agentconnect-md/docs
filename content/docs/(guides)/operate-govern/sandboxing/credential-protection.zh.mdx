icon: LockKeyhole
description: "了解 AgentConnect 如何把代码托管平台令牌、提供方 API 密钥和已保存的登录凭证挡在 Agent 会话之外。"
---

只要条件允许，Daemon 都会尽量避免把真实凭证直接放进 Agent 会话。会话里拿到的只是占位符，当请求发往对应目标地址时，Daemon 的凭证代理再把占位符替换成真实凭证。这样一来，即便 Agent 读取了环境变量或本地文件，拿到的内容在其他地方也无法使用。

## 代码托管平台凭证 [#code-host-credentials]

GitHub、GitLab 和 Gitea 的访问在所有执行环境中都采用这套机制，包括主机、`srt`、`microsandbox`、Kubernetes 池中的 Pod，以及通过 [Daemon 组](/build-your-team/daemons/daemon-groups)调度到其他成员机器上运行的会话，无需手动开启。

- `git`、`gh` 和 `glab` 可以正常使用。代理会自动附加一个短期令牌，权限限定为请求指向的仓库，以及 Agent 在该仓库上的[访问级别](/build-your-team/agents/workspaces-and-repos#repository-credentials)。
- 会话的环境变量、Git 配置和文件中不包含任何可用令牌。
- 显式配置给 Agent 的令牌（例如它自己的 `GH_TOKEN` 或 `GITLAB_TOKEN` [密钥](/build-your-team/variables-and-secrets)）会原样透传。
- 旧版的 `gh-token`、`glab-token` 辅助命令以及 `gh`、`glab` 包装器已经移除，脚本请直接调用 `git`、`gh` 或 `glab`。

### 代理会拒绝的请求 [#what-the-proxy-refuses]

| 请求 | 结果 |
| --- | --- |
| GitHub GraphQL 变更（mutation） | 拒绝：GraphQL 仅允许只读。报错会指明对应的代码托管平台写入工具（Pull Request、Issue、评论、评审），Agent 会改用该工具重试。 |
| GitLab 或 Gitea 的 API 写操作 | 拒绝，并指明对应的写入工具。API 读操作不受影响。 |
| 向只读仓库执行 `git push` | 拒绝，并提示 Agent 缺少写权限。如需推送，请授予**读写**权限。 |
| 未指定目标仓库的 REST 写操作 | 拒绝。针对具体仓库的 GitHub REST 写操作（如 `gh api`）会按 Agent 的访问级别放行。 |

创建或修改 GitHub Projects 条目和 Discussions 只能通过 GraphQL 写操作完成，因此 Agent 无法执行这些写入，但读取操作不受影响。

如果会话连不上代理（例如使用的 Kubernetes Runtime 镜像版本低于 Daemon），会话会在不带代码托管平台凭证的情况下启动，Daemon 会在日志中记录原因。

## 提供方 API 密钥 [#provider-api-keys]

模型提供方的 API 密钥也走同一个代理：Runtime 拿到的只是占位符，请求发往提供方之前，由代理把真实密钥填进去。

| 密钥 | 适用的会话 |
| --- | --- |
| 组织的**基础设施 → Provider keys**，用于**模型登录**设为 **Provider key** 的 Agent | 主机、`srt` 和 `microsandbox`，包括 Daemon 组调度到其他成员上运行的主机会话 |
| Daemon 所在机器上的 API 密钥，适用于[下表](#protection-by-runtime)中标为**代理**的 Runtime | `srt` 和 `microsandbox` |
| Kubernetes 安装实例的密钥：`daemonPool.modelCredentials`、`modelEgress.clients.<client>.apiKey`，以及在 `daemonPool.runtimeEnvironment` 中映射的 `ANTHROPIC_API_KEY`、`OPENAI_API_KEY`、`DEEPSEEK_API_KEY` 或 `COPILOT_PROVIDER_API_KEY` | 池中的 Pod（[详情](/self-hosting/kubernetes/runtime-authentication#keys-stay-with-the-daemon-pool)） |

组织密钥上配置的额外请求头也由代理统一注入，不会进入会话。如果修改了密钥的端点，需要开启新会话才能生效。

以下几类凭证仍会按原样传入会话：

- 端点是明文 `http://` 的密钥（占位符替换仅在 HTTPS 连接上生效）
- Daemon 无法为该 Runtime 匹配到唯一 HTTPS 端点的密钥，例如使用了自定义端口的密钥（Daemon 会记录一次告警日志）
- 由密钥服务器为单个会话签发的短期密钥
- 订阅和 OAuth 登录（详见[下文](#oauth-and-tool-rules)）
- 主机会话中 Daemon 宿主机本地的密钥，因为主机会话本身就能直接读取宿主机文件

## 信任与网络 [#trust-and-network]

由于代理需要终结发往代码托管平台和模型提供方的 TLS 连接，会话必须信任 Daemon 生成的证书颁发机构（CA）。Daemon 会把标准的信任环境变量（`SSL_CERT_FILE`、`NODE_EXTRA_CA_CERTS`、`GIT_SSL_CAINFO`、`REQUESTS_CA_BUNDLE`）指向一个合并后的证书包，里面包含系统根证书、Daemon 的 CA，以及运维人员或会话变量原本指定的 CA。

会话通过 `HTTPS_PROXY` 连接到代理。如果某个客户端忽略了 `HTTPS_PROXY` 或固定校验自带证书，就会直接带着占位符去连代码托管平台或提供方，结果会被对方拒绝。

运维侧需要注意以下几点：

- **出站访问**：上游请求由 Daemon 发出，因此 Daemon 必须能通过 HTTPS 访问旗下 Agent 用到的所有代码托管平台和提供方端点。在 Kubernetes 中，这一要求针对的是 Daemon 池，而不是 Agent Pod。
- **私有 CA**：代理使用 Daemon 的系统信任根以及[为 Daemon 配置的私有 CA](/self-hosting/docker-compose/configuration#private-certificate-authorities)来校验上游证书。
- **出站代理**：如果 Daemon 本身需要通过 `HTTPS_PROXY` 访问外网，凭证代理的上游请求也会经过它，同时遵守 `NO_PROXY`。

## 按 Runtime 划分的保护 [#protection-by-runtime]

本页余下内容适用于自托管 Linux Daemon 上保存的登录凭证。具体保护方式取决于 Runtime 和登录方式，在 `srt` 和 `microsandbox` 下表现一致。

| Runtime | OAuth | API 密钥 |
| --- | --- | --- |
| Claude Code | 工具规则 | 代理 |
| Codex | 工具规则 | 代理 |
| DeepSeek Harness | 不适用 | 代理 |
| OpenCode | 无防护 | 代理 |
| pi | 无防护 | 代理 |
| Grok Build | 无防护 | 代理 |
| Qwen Code | 无防护 | 代理 |
| Oh My Pi | 无防护 | 代理 |
| Amp | 不适用 | 代理 |
| Kimi Code | 无防护 | 代理 |
| Cline | 无防护 | 代理 |
| Devin | 无防护 | 不适用 |
| Antigravity ACP | 无防护 | 代理 |
| GitHub Copilot | 无防护 | 代理 |
| Qoder CLI | 无防护 | 无防护 |
| Qoder CN CLI | 无防护 | 无防护 |

- **工具规则**：Runtime 会阻止内置工具读取或修改受保护的凭证文件。
- **代理**：真实 API 密钥保留在宿主机上（支持的来源见下表）。
- **无防护**：沙箱内的工具可以直接读取该凭证。
- **不适用**：该集成不涉及这种登录方式。

Claude Code 和 Codex 在启用 API 代理时，其工具规则也会保持生效。

## OAuth 与工具规则 [#oauth-and-tool-rules]

OAuth 凭证会被挂载或复制到会话中，由 Runtime 自行处理认证和令牌刷新。

Claude Code 和 Codex 在 SRT 和 `microsandbox` 中使用相同的工具规则。Claude Code 会限制 Bash 和文件工具（包括 Read 和 Edit），Codex 则通过权限配置文件禁止工具访问凭证路径。Runtime 进程本身仍可读取这些凭证以完成身份认证。

这些规则只约束 Runtime 的内置工具，不涵盖任意辅助进程或 MCP 服务器。其他 Runtime 在接收 OAuth 凭证时没有额外的工具级防护。

## API 密钥代理 [#api-key-proxy]

对于支持代理的登录方式，Daemon 只向会话提供占位符。宿主机上的代理仅在请求发往提供方已批准的 HTTPS 端点时，把请求头里的占位符替换为真实密钥。

在 `srt` 和 `microsandbox` 中，这覆盖下表列出的所有已保存密钥，也覆盖在 Daemon 环境变量或 Runtime 定义中配置的密钥：Claude Code 的 `ANTHROPIC_API_KEY`、Codex 的 `OPENAI_API_KEY`、DeepSeek Harness 的 `DEEPSEEK_API_KEY`，以及 GitHub Copilot 和 Antigravity ACP 的密钥。在 `srt` 中，同样覆盖 OpenCode 的这些环境变量。

导入到沙箱里的凭证文件只包含占位符。对于 Oh My Pi，Daemon 会在写入任何 API 密钥记录之前先创建一个带占位符的私有 SQLite 数据库。宿主机上的原始登录文件不会被修改。

代理只读取宿主机上的提供方配置，因此在沙箱内修改配置无法把密钥重定向到其他地址。已授权的提供方会收到真实密钥，其返回内容不做脱敏处理。

### 支持的已保存密钥 [#supported-saved-keys]

| Runtime          | 密钥来源                                                                      |
| ---------------- | ----------------------------------------------------------------------------- |
| Claude Code      | 当前生效的全局配置中的 `primaryApiKey`                                        |
| Codex            | `CODEX_HOME/auth.json` 中的 `OPENAI_API_KEY`                                  |
| DeepSeek Harness | `.dsh/.credentials.yaml` 或 `.dsh/.env` 中的标准 `DEEPSEEK_API_KEY` 条目      |
| OpenCode         | `auth.json` 中的 API 记录（`type: api`）                                      |
| pi               | `auth.json` 中的 API 记录，或 `models.json` 中的提供方密钥                    |
| Grok Build       | `config.toml` 中的按模型密钥（`model.<id>.api_key`）                          |
| Qwen Code        | `settings.json` 中的模型提供方密钥（包括旧版的 `security.auth.apiKey`）       |
| Oh My Pi         | `agent.db` 中的 API 密钥记录                                                  |
| Amp              | `secrets.json` 中的原生 CLI 条目（`apiKey@<service URL>`）                    |
| Kimi Code        | `.kimi-code/config.toml` 中的提供方密钥（`providers.<name>.api_key`）         |
| Cline            | `providers.json` 中各提供方的 API 密钥（`apiKey` 或 `auth.apiKey`）           |
| GitHub Copilot   | `COPILOT_PROVIDER_API_KEY`，发往 `COPILOT_PROVIDER_BASE_URL`                  |
| Antigravity ACP  | `GEMINI_API_KEY`（`gemini-api-key` 登录方式）                                 |

### 提供方限制 [#provider-limits]

- **DeepSeek** 固定使用 `https://api.deepseek.com`，启动时会拒绝自定义端点。
- **Grok、Qwen 和 Kimi Code** 需要在宿主机配置中显式指定 HTTPS 端点（Kimi Code 对应提供方的 `base_url`）。
- **Claude Code、Codex、OpenCode 和 pi** 使用受支持的宿主机提供方配置或内置默认端点。自定义 Codex 提供方必须设置 `requires_openai_auth = true`。
- **Oh My Pi** 使用内置的提供方默认端点。
- **pi、Oh My Pi 和 Cline** 支持 Anthropic、OpenAI、DeepSeek、Google、xAI、OpenRouter、Groq 和 Mistral 的默认端点。Cline 的其他提供方需要在提供方条目中配置 HTTPS `baseUrl`。
- **GitHub Copilot** 需要 HTTPS 的 `COPILOT_PROVIDER_BASE_URL`。
- **Antigravity ACP** 默认使用 Gemini API；如果 `GOOGLE_GEMINI_BASE_URL` 设为 HTTPS 端点，则改用该端点。

如果识别出的 API 密钥没有匹配的受支持路由，密钥会被隐藏，对应的提供方也无法使用（在 OpenCode 中，其他已配置的提供方仍可正常工作）。

代理保护仅覆盖上表列出的已保存来源，不会自动覆盖系统密钥环、通过命令动态获取的密钥、任意自定义请求头、自定义插件，或在沙箱内新执行的登录。此外，Amp 单独的 `amp-acp/credentials.json` 登录、仅保存在自定义模型文件中的 Oh My Pi 密钥、Cline 的 AWS 凭证和自定义请求头，以及通过环境变量读取密钥（`api_key_env`）的 Kimi Code 提供方，均不在此保护范围内。

Qoder CLI 和 Qoder CN CLI 的密钥目前不受代理保护：个人访问令牌是在请求体中交换的，而服务账号密钥有固定格式校验，占位符无法通过。Devin 仅支持浏览器登录，没有单独的 API 密钥登录方式。

受支持的端点必须使用 HTTPS，且不能包含自定义端口或内嵌在 URL 中的凭证。受保护的会话会拒绝自定义的 TLS 信任覆盖以及与凭证冲突的挂载。

## 现有会话与密钥变更 [#existing-sessions-and-key-changes]

受保护的虚拟机在停止并重新恢复时会加载更新后的宿主机密钥，正在运行中的虚拟机则继续使用原有密钥。如果修改了登录账号、提供方记录或凭证布局，可能会触发虚拟机重建（详见[哪些内容会保留](/operate-govern/sandboxing#runtime-image)）。
