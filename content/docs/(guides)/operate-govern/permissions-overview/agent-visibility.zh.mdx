Agent 可以把任务委派给其他 Agent。**Agent 可见范围**控制允许哪些 Agent 相互调用，系统会在发现阶段和任务投递阶段分别做校验。

可以把它理解为*这个 Agent 能看到哪些其他 Agent*：这项策略针对的是 Agent，而不是人。它与团队可见范围、会话可见范围不同，后两者控制的都是**人**能访问什么。

<Image src={imgAgentVisibilityDefault} alt="组织设置中的默认 Agent 可见性" width={760} />

它与[团队可见范围](/operate-govern/permissions-overview/team-visibility)相互独立，后者控制哪些**人**能看到某个 Agent。

## 两个方向 [#two-directions]

每个 Agent 都有入站和出站两项独立策略：

| 方向 | 控制台中的问题 | 用途 |
| --- | --- | --- |
| 入站 | **哪些 Agent 可以调用此 Agent**？ | 允许调用它的 Agent |
| 出站 | **此 Agent 可以调用哪些 Agent**？ | 它允许委派的目标 Agent |

每个方向都可以设为：

- **所有 Agent**（默认）
- **已选择**：手动指定一份 Agent 列表

如果设为**已选择**但列表为空，表示该方向上不允许任何 Agent 互通。

## 新建 Agent 的默认值 [#defaults-for-new-agents]

默认情况下，组织新建的 Agent 在入站和出站两个方向上都是**所有 Agent**，可以发现并调用组织内其他可被调用的 Agent。

组织所有者可以在**设置**页面的**默认 Agent 可见性**卡片中修改这项默认值：

- **所有 Agent**：之后新建的 Agent 在两个方向上默认对组织内所有 Agent 开放。
- **隔离**：之后新建的 Agent 在两个方向上默认都是**已选择**且列表为空。在手动配置之前，它们既无法发现其他 Agent，也不接受任何调用。

修改默认值只影响之后新建的 Agent，不会改动已有 Agent 的策略。创建新 Agent 时，也可以在**添加 Agent → 访问权限**中单独覆盖任一方向。

## 如何判定一次调用 [#how-a-call-is-decided]

Agent A 要成功调用 Agent B，必须同时满足以下三个条件：

1. A 和 B 属于同一个组织。
2. A 的出站策略允许调用 B。
3. B 的入站策略允许接受 A 的调用。

两侧策略必须同时满足。把 B 加到 A 的出站列表里，无法绕过 B 的入站限制；把 A 加到 B 的入站列表里，也不会扩大 A 的出站范围。

例如，规划 Agent 被允许调用 `frontend` 和 `backend`，而 `payments` 只接受故障协调 Agent 的调用。除非两边都修改策略，否则规划 Agent 既发现不了也调用不了 `payments`。

## 组织范围的发现 [#organization-scoped-discovery]

Agent 可以在整个组织内发现策略允许的其他 Agent 并向其委派任务。它们不需要在同一个 Slack 频道、共享同一个聊天集成，甚至不需要运行在同一个 Daemon 上。即使某个 Agent 没有配置任何聊天集成，也可以被正常发现和调用。

面向人的[团队可见范围](/operate-govern/permissions-overview/team-visibility)是另一套独立边界。对部分成员隐藏某个 Agent 不会改变 Agent 之间的调用关系；反过来，允许两个 Agent 相互调用，也不会把任何一方的控制台资源暴露给更多人。

## 配置方法 [#configure-it]

创建或编辑 Agent 时，在**访问权限 → Agent 可见性**中设置入站和出站策略。Agent 详情页会列出策略允许的入站和出站 Agent，Agents 页面则会用拓扑图直观展示当前的调用关系。

<Image src={imgAgentTopology} alt="Agents 页面上的拓扑视图，显示已配置的调用图" width={900} />

关于委派如何与路由、分层专家和扇出模式配合使用，请参阅[多 Agent 工作模式](/build-your-team/agents/multi-agent-work-modes#agent-to-agent-delegation)。
