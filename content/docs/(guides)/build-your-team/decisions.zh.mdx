**决策**（Decision）针对收到的消息判断一个明确的问题，并返回一个结构化结果：**是 / 否**、你预设的某个分类，或一个数值评分。决策本身只定义问题；根据结果采取什么动作，由使用它的场景决定：频道可以决定是否回复，共享机器人可以把新对话路由给对应的专项 Agent，仓库可以挑选评审 Agent，Agent 也可以为新会话动态选择 Runtime 和模型。

决策由 TypeSafe 的判断模型 [Jev](https://docs.typesafe.ai/introduction) 执行评估。Jev 不生成长段文本，而是在一秒内为每个可能结果给出概率。评估在服务该 Agent 的 Daemon 上运行，不会开启会话，结果本身也不会赋予任何额外权限。

## 配置 Provider [#set-up-the-provider]

计费方式取决于评估运行的位置：

- **AgentConnect Cloud**：运行在 Cloud 托管基础设施上的 Agent 开箱即用，无需额外配置。每次评估按 TypeSafe 公布的价格从组织余额扣费，与其他[云端模型用量](/build-your-team/daemons/manage-daemons#pricing)一致。
- **你自己的 Daemon**（含所有[自托管](/self-hosting)部署）：由组织所有者打开**基础设施 → Provider keys**，为 **TypeSafe (Jev)** 添加 API key。如需改用自定义端点或附加请求头，可在**连接设置**中配置。

只要配置了 API key，系统就会优先使用它（Cloud 上的 Agent 同样如此），对应评估不再从余额扣费。该 key 为只写密钥：控制平面将它与其他只写密钥一并保存，只在对应 Daemon 为你的 Agent 执行评估时下发。自托管部署需先配置[密钥加密](/self-hosting/docker-compose/configuration#secret-storage)才会对密钥做静态加密，否则默认以明文存在 PostgreSQL 中。保存 key 时不会自动校验，请在决策编辑器里运行一次示例确认可用。

## 创建决策 [#create-a-decision]

打开**决策**页面，点击**添加决策**。列表为空时，页面会提供现成的示例模板（Needs reply、Spam、Support category、Issue type、PR focus、PR author 和 Task complexity），可以直接添加并按需修改。

你也可以在单 Agent 的 [Playground 对话](/build-your-team/agents/playground#configure-agentconnect-from-a-conversation)中描述判断需求，让 Agent 帮你起草决策。批准创建后，回到这里用示例测试效果。

<Image src={imgDecisionEditor} alt="决策编辑器：一个选项问题及其判定标准，以及用示例试运行得到的每个答案的概率" width={900} />

| 字段 | 作用 |
| --- | --- |
| **名称** | 决策在各个配置入口中显示的名称 |
| **Provider · 模型** | 所用的 Jev 模型：**Jev 1.13**、**Jev latest** 或 **Jev preview** |
| **问题类型** | **选项**返回你定义的某个 key，**布尔值**返回是或否，**评分**返回指定刻度内的数值（支持小数） |
| **指令** | 要判断的具体问题。写清指向哪条消息（例如“最新一条消息”），系统会自动附带对话中更早的历史消息 |
| **判定标准** | 定义每个结果的含义：2–32 个选项 key、是与否，或 2–10 个有序评分等级 |
| **可见性** | **所有人**，或**指定成员**及组织所有者 |

**用示例试运行**会对一段模拟对话做真实评估。选好**运行位置**（Daemon），填入可选的**对话历史**和**当前消息**，点击**运行**即可看到各结果的概率、所用模型以及发送的上下文长度。这里的预览只说明决策本身会给出什么结果；该结果是否触发 Agent，取决于挂载处的规则，每个挂载处都有各自的试运行预览。

同一个决策可以在多处复用。**最近评估**卡片会列出所有挂载位置及其最近一次的评估结果。编辑问题会影响所有使用该决策的地方。如果修改判定标准导致某处规则引用了已删除的选项，该处会显示**需要复核**并暂停评估，直到修复为止。仍被引用中的决策无法删除。

## 在哪里使用决策 [#where-to-use-a-decision]

| 位置 | 在哪里设置 | 答案决定什么 |
| --- | --- | --- |
| [聊天频道](#respond-in-a-channel) | Agent 的**集成**标签页 → 频道行 → **添加决策** | Agent 是否回复 |
| [共享机器人](#route-a-shared-bot) | **集成** → 共享机器人 → **默认分发** → **或按决策选择** | 哪些 Agent 接手新对话 |
| [Issue 和 Pull Request](#pick-agents-for-issues-and-pull-requests) | Agent 的 GitHub、GitLab 或 Gitea 事件行 → **添加决策** | 哪些关注该仓库的 Agent 接手 |
| [Agent 的 Runtime](#choose-a-runtime-and-model) | **编辑** Agent → **Runtime** → **按决策** | 每个新会话的 Runtime 和模型 |
| [Agent 的工具](#let-an-agent-ask) | Agent → **工具与技能** → **Decisions** | 由 Agent 自己决定如何使用答案 |

频道、共享机器人、仓库和 Runtime 还可以[串联决策](#chain-decisions)，在第一个问题之后再问第二个。

### 在频道中回复 [#respond-in-a-channel]

**按决策**是与 **@ 提及**、**所有消息**、**关闭**并列的频道触发方式，适用于所有聊天平台的频道和群聊以及 Linear 的团队行，一对一私信仍保留**开启 / 关闭**开关。在频道行点击**添加决策**，选中决策后设置**触发条件**：

- **布尔值**：选择是、否，或两者都选。
- **选项**：选择会触发 Agent 的结果，并为每个结果设置最低概率阈值。只要任意选中项达到对应阈值，就会触发 Agent 一次，即使它不是概率最高的结果。
- **评分**：在刻度上设定**从** / **到**的数值区间。

<Image src={imgDecisionChannelRules} alt="频道的按决策规则：technical 至少 30% 时触发，试运行的消息会触发 Agent" width={560} />

每条新的顶层消息都会触发判断，包括 @ 提及该 Agent 的消息（提及只决定哪个 Agent 可以回复）。Agent 已加入的线程中的后续回复会直接继续，不再重新评估。被跳过的消息不会启动运行，但会保留在对话历史中，供后续评估和 Agent 读取。**试一条消息**可以按当前规则预览示例消息是**会触发**还是会被跳过。

### 路由共享机器人 [#route-a-shared-bot]

使用 HTTP 回调、同时服务多个 Agent 的[共享 Slack 机器人](/how-to-guides/one-slack-app-across-channels)，可以按对话动态选择 Agent，而不必按频道固定绑定。在**集成**页面展开该机器人，打开频道的**默认分发**，选择**或按决策选择**。每条规则把对应结果指向该机器人下的某个 Agent 或设为**不触发**；无规则命中时执行**否则**分支，可选**使用默认 Agent** 或**不触发**。

- 对于选项问题，所有达到最低概率阈值的规则都会命中，因此一条消息可能同时触发多个 Agent。每个 Agent 最多启动一次，命中的**不触发**规则不会抵消其他已命中的规则。
- 路由规则只作用于未指定任何 Agent 的新对话。明确提及或已有线程会沿用原来的 Agent，但依然会接受判断，跳过规则同样生效。
- **路由已暂停**会暂停该路由覆盖的所有频道中的新投递（包括提及和线程回复），正在运行的轮次会照常完成。
- **试一条消息**会打开**测试路由**，方便在保存前预览新对话、明确提及或已有线程三种场景的路由结果。

<Image src={imgDecisionSharedBotRouting} alt="共享机器人的按决策规则：billing 和 technical 达到 30% 时分别路由给对应 Agent，测试消息同时命中两条" width={640} />

### 为 Issue 和 Pull Request 挑选 Agent [#pick-agents-for-issues-and-pull-requests]

当多个 Agent 关注同一个仓库时，可以用决策指定哪些 Agent 接手各个 Issue 或 Pull Request（GitLab 上为 Merge Request）。在 Agent 的 [GitHub](/connect-automate/triggers-automation/github)、[GitLab](/connect-automate/triggers-automation/gitlab) 或 [Gitea](/connect-automate/triggers-automation/gitea) 集成中，点击 Issue 或 Pull Request 事件行上的**添加决策**。规则按仓库和事件类型生效，由所有关注该仓库的 Agent 共用，修改规则需要对所有这些 Agent 都具备编辑权限。

决策会读取标题、描述和讨论内容；对于 Pull Request，可用时还会读取提交记录和 diff。每次更新都会经过评估，事件行原本的触发条件不再生效。提及同样无法绕过决策：带提及的事件仍会进入评估，以决策结果为准。**否则**分支可设为交给所有关注该仓库的 Agent（与未配置决策时一致），或不触发任何 Agent。如果决策需要复核或已不可用，该仓库上新的 Issue 和 Pull Request 会暂缓处理，直到修复规则或移除该决策。

### 选择 Runtime 和模型 [#choose-a-runtime-and-model]

在 Agent 的**编辑**对话框中，将 **Runtime** 从**固定**改为**按决策**。每条规则把对应结果映射到一个 Provider 和模型，并可单独配置推理强度、审批策略和快速模式；**兜底 Provider 和模型**处理其余未命中情况。对于选项问题，达到阈值且概率最高的结果胜出。

评审 Agent 可以借此实现跨模型评审，直接使用 **PR author** 示例即可：Claude 编写的 Pull Request 交给 Codex 模型评审，Codex 或 Grok 编写的交给 Claude 模型评审。

<Image src={imgDecisionRuntime} alt="用 PR author 决策按决策选择 Runtime：Claude 写的 Pull Request 用 gpt-5.5，Codex 或 Grok 写的用 opus，兜底为 sonnet" width={620} />

决策仅在新会话启动时评估一次，输入为触发消息（Issue 和 Pull Request 会一并带上主题与历史记录）。已有会话保持启动时选定的 Runtime 和模型。**试用样例**可以演示规则匹配逻辑，不会真正调用模型。

### 让 Agent 自己提问 [#let-an-agent-ask]

在 Agent 的**工具与技能 → Decisions** 卡片中挂载决策后，Agent 就能在运行轮次中自行调用评估，例如先给工单分类再决定处理流程。调用时的上下文由 Agent 提供。返回结果仅作为参考信息，不会给 Agent 赋予任何额外权限。

### 串联决策 [#chain-decisions]

有些判断拆成两步更清晰。例如支持 Agent 仅在遇到技术问题且用户情绪激动时才介入：先用 **Support category**，命中 **technical** 后再运行 **Customer frustration** 判断评分是否在 2 到 3 之间。在频道规则的**命中条件**或**否则**旁，或在共享机器人、仓库、Runtime 规则的任意一行旁，点击**继续判断下一个 Decision**，再在弹出的面板中设置下一步的条件即可。

<Image src={imgDecisionChain} alt="频道的按决策规则：technical 达到 50% 后继续判断 Customer frustration 决策" width={560} />

串联后的步骤会显示为标签，点击即可编辑。一条决策链最多支持八个决策，所有步骤共用五秒总超时，因此串联的步骤越多，Agent 启动前的等待时间越长。

## 决策无法给出答案时 [#when-a-decision-cannot-answer]

当 Provider 出错或超时、缺少可用的 API key 或余额，或 Daemon 满载时，评估会返回**评估不可用**。评估不可用永远不会被当成“否”或“跳过”：

| 位置 | 实际会发生什么 |
| --- | --- |
| 聊天频道 | 消息照常交给 Agent，按触发处理 |
| 共享机器人 | 已指定或正在继续的 Agent 正常接收消息；新对话交给频道的默认 Agent，即使**否则**设为**不触发** |
| Issue 和 Pull Request | 所有关注该仓库的 Agent 都会接手该事件，与未配置决策时一致 |
| Runtime | 会话使用兜底 Provider 和模型启动 |

当挂载点完全无法执行决策时，对应行会标明原因：**等待同步**、**需要复核**、**Daemon 离线**、**不受支持**（需升级 Daemon 或 Relay）或**访问已撤销**。
