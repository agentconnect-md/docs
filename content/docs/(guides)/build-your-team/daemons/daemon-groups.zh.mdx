<Callout type="info">
**大规模运行 Agent 时，推荐使用 Kubernetes。**[Kubernetes 部署](/self-hosting/kubernetes/deploy)面向生产环境设计：集群级 Daemon 池让 Agent 在可随时替换的节点之间持续运行，每个会话都在独立的沙箱 Pod 中访问同一份共享存储，无需逐台机器配置。如果你的 Agent 运行在自己维护的多台机器上，再使用 Daemon 组。
</Callout>

**Daemon 组**是连接到你组织的一组 Daemon。把 Agent 分配到组而不是单台 Daemon，可以获得两项独立的能力：

| 功能 | 作用 | 开启方式 |
| --- | --- | --- |
| [**故障转移**](#failover) | 同一时间由一个成员为 Agent 提供服务。当该成员停止时，另一个成员自动接管。 | 用两台或更多 Daemon 创建一个组，并将 Agent 分配到该组。 |
| [**并行会话**](#parallel-sessions) | Agent 的隔离会话可以调度到组内其他成员上运行，不再局限于当前服务成员。 | 为该组开启**在组内分散会话**，并在每台愿意分担会话的机器上开启 `sandbox.share`。 |

故障转移可以单独使用，不依赖并行会话。并行会话建立在故障转移之上，只对分配在组上的 Agent 生效。

## 开始之前 [#before-you-start]

**创建组**：打开**基础设施**，进入 **Daemon 组**，点击**新建组**。输入名称、选择成员 Daemon；除非准备启用[并行会话](#parallel-sessions)，否则保持**在组内分散会话**关闭。每台 Daemon 同一时间只能加入一个组。你也可以在某台 Daemon 的详情页通过 **加入 \<group\>** 和 **离开 \<group\>** 来调整归属。

加入组不会迁移现有 Agent。原本直接分配在这台 Daemon 上的 Agent 会继续在原地运行，并在组的页面上标记为**固定**。离开组时，原本由该成员服务的组内 Agent 会交接给其余成员。

组的页面会展示所有成员、当前处于**服务中**的成员、组上的 Agent 以及活跃会话。**Runtime** 列表只显示所有服务中成员都共同具备的 Runtime，因为组上的 Agent 随时可能由任一服务中成员接管。

<Image src={imgDaemonGroup} alt="Daemon 组的页面：两个服务中的成员、它们的负载和固定的 Agent，以及每个服务中成员都提供的 Runtime" width={820} />

## 故障转移 [#failover]

### 作用 [#what-it-does]

分配在组上的 Agent 同一时间只由一个成员提供服务，该成员负责执行轮次、维持聊天平台连接，以及触发定时任务和事件。一旦该成员停止服务，另一个成员会自动接管，按需安装该 Agent 并继续运行：

- **重启或升级**：该成员会先排空任务，排空完成后另一成员立即接管。
- **意外失联**（崩溃、断电或断网）：原成员会持有该 Agent 直到租约过期（约 2 分钟），随后由其他成员接管。

接管完成后，Agent 会继续留在新成员上运行。即使原成员稍后恢复，Agent 也不会自动迁回，系统也不会在成员间做重新平衡。

### 设置步骤 [#set-it-up]

1. 连接两台或更多 Daemon，并[创建一个组](#before-you-start)。
2. 确保每个成员都具备运行该 Agent 的条件：已安装并登录对应的 Runtime、可用的 MCP 服务器，以及支持其[执行策略](/operate-govern/sandboxing#pick-an-execution-strategy)。组的 **Runtime** 列表展示所有服务中成员共同支持的 Runtime；**执行策略**选择器则列出至少有一个服务中成员支持的策略。如果某个会话落到了不支持该策略的成员上，该成员会直接拒绝，而不会降级到更弱的隔离级别。
3. 将 Agent 分配到组：在 Agent 的**配置**页中，把**运行位置**选为该组。选择器会提示：“该分组中任意一个 Daemon 都可以为此 agent 服务。”

你也可以在创建 Agent 时直接指定运行在组上。

<Image src={imgRunsOnGroup} alt="运行位置选择器，在单个 Daemon 旁列出了一个 Daemon 组" width={560} />

### 哪些会随之转移，哪些不会 [#what-carries-over-and-what-doesnt]

| 会转移到新成员 | 留在原成员本地 |
| --- | --- |
| Agent 已保存的配置定义、集成、定时任务和触发器 | 对话的会话记录和各会话的 Runtime 状态 |
| 托管记忆（组上 Agent 的托管记忆保存在 AgentConnect 中） | Runtime 自身的原生记忆 |
| GitHub、GitLab 和 Gitea 工作区（会在新成员上重新克隆） | 临时空白工作区，以及任意工作区中尚未提交的改动 |

实际使用中，故障转移后继续对话会在新成员上启动一个全新的 Runtime 会话。如果某条 Webchat 对话原本运行在旧成员上，界面会明确提示发生了切换，不会在缺失上下文的情况下强行作答。希望在故障转移后保留的代码改动，请及时提交并推送。

对于组上的 Agent，托管记忆始终存放在 AgentConnect 中而不是单台 Daemon 本地，因此每个成员看到的记忆完全一致。

### 可选：共享会话历史 [#optional-share-session-history]

默认情况下，每个成员把会话记录存在各自的本地数据库里。如果希望无论哪个成员接管 Agent 都能看到完整的会话条目和记录，可以让成员共享同一个 PostgreSQL 数据库。在 Daemon 根目录下（与 `config.json` 同级）创建连接配置文件：

```json
{ "version": 1, "databaseUrl": "postgresql://agentconnect:<password>@db.example.test:5432/agentconnect", "maxConnections": 4 }
```

然后在 `config.json` 中指向该文件：

```json
{ "store": { "backend": "postgres", "configFile": "data-plane.json" } }
```

在组内每台成员上都指向同一个数据库并重启 Daemon。请限制连接文件的权限，仅允许运行 Daemon 的系统用户读取。

- 存储后端是机器级配置，会影响该 Daemon 上的所有 Agent，不仅限于组上的 Agent。
- 该模式需要连接控制平面，仅定义在机器本地 Agent 目录里的 Agent 不会使用它。
- 切换后端不会自动迁移历史数据：改用 PostgreSQL 后，Daemon 会从空白历史开始记录。
- 共享存储只保存会话记录，不包含 Runtime 进程状态。故障转移后，原本在旧成员上运行的 Runtime 会话仍会全新启动，除非该会话原本就是通过[并行会话](#parallel-sessions)运行在另一台成员上的。

## 并行会话 [#parallel-sessions]

### 作用 [#what-it-does-1]

未开启并行会话时，Agent 的所有会话都在当前服务成员上运行。开启并行会话后，每新建一个**隔离**会话，系统会根据各机器的[会话容量](#size-each-machine)计算负载比例，把新会话放到加入后负载率最低的成员上。已满载的成员会被跳过，负载率相同时优先留在服务成员上。当所有机器容量相同时（默认情况），规则就等价于选择当前隔离会话数最少的成员。会话一旦启动就会固定在这台机器上运行直到结束，服务成员继续负责对话接入并将消息转发过去。

会话在另一台机器上的运行方式取决于 Agent 的**执行策略**：

| 执行策略 | 在其他成员上的运行方式 |
| --- | --- |
| `host` | 在该机器上以独立进程运行，使用专属会话目录（仅支持 Linux）。 |
| `microsandbox` | 在该机器上启动 microsandbox 虚拟机（需该机器支持 microsandbox）。 |
| `srt` | 在该机器上启动 SRT 沙箱（需该机器支持 `srt`）。 |

### 要求 [#requirements]

- Agent 已分配到组（已完成[故障转移](#set-it-up)配置）。
- 每个会话使用独立工作区：已开启**工作树**（当执行策略为沙箱时，界面显示为**会话隔离**）。共用同一个工作区的会话始终留在服务成员上运行。
- 分担会话的成员必须支持该 Agent 的执行策略、已登录对应 Runtime，且目标模型可用；不满足条件的成员会被跳过。
- 成员之间可以通过 TCP 直连。共享容量的成员启动时会在所有网卡上监听一个随机端口，其他成员会通过该 Daemon 连接 AgentConnect 时使用的地址来访问它，因此需要在防火墙中放行成员之间的入站连接。

### 开启 [#turn-it-on]

并行会话需要在两处分别确认开启：

1. **组级别**：打开**编辑组**，开启**在组内分散会话**。关闭状态下，组内任何 Agent 的会话都不会调度到其他成员。

   <Image src={imgDaemonGroupEdit} alt="编辑组：选中了两个 Daemon，并打开了“在组内分散会话”" width={420} />

2. **单机级别**：在每台愿意承接其他成员会话的机器上，将以下配置加入 `config.json` 并重启 Daemon：

   ```json
   { "sandbox": { "share": true } }
   ```

   是否共享算力应由机器所有者决定，因此这项配置只存在于本地配置文件中，在 Daemon 启动时读取，无法从控制台修改，默认关闭。

未开启 `sandbox.share` 的成员仍可正常为组内 Agent 提供服务并运行自己的会话，只是不会接手其他成员的会话。

### 为每台机器设置容量 [#size-each-machine]

每个成员的会话容量由 `config.json` 中的 `limits.maxConcurrentSessions` 控制，默认为 32。它定义了该机器为组内运行的并发会话上限（包含自身的隔离会话），也决定了它分得新会话的比例。如果组内机器规格不同，可以按硬件能力设置成比例的上限并重启 Daemon。例如一台高配工作站搭配两台较小的机器：

| 机器 | `config.json` |
| --- | --- |
| 128 GB 工作站 | `{ "limits": { "maxConcurrentSessions": 8 } }` |
| 32 GB 机器 | `{ "limits": { "maxConcurrentSessions": 2 } }` |
| 16 GB 机器 | `{ "limits": { "maxConcurrentSessions": 1 } }` |

这样工作站就会承接更大比例的新会话。和 `sandbox.share` 一样，容量上限属于本机配置，无法从控制台修改。达到容量上限时只会拒收来自其他成员的会话，本机自身服务的会话仍可照常运行。

### 共享一台机器会提供什么 [#what-sharing-a-machine-lends]

- **本机的 Runtime 登录态**：调度到这台机器上的会话会使用本机的 Runtime 登录或 API 密钥（例如 Codex 或 Claude 登录）以及沙箱配置。Agent 自身的提供方凭证、密钥和代码仓库凭证仍由服务成员通过加密连接下发。请只在你放心让组内 Agent 共用其 Runtime 账号的机器上开启共享。
- **CPU、内存和磁盘资源**，上限受本机[会话容量](#size-each-machine)控制。
- **一个监听端口**，详见[要求](#requirements)。

### 查看会话在哪里运行 [#see-where-a-session-runs]

在会话的**详情**面板中，**运行于**字段会显示实际运行该会话的机器。如果会话留在了服务成员上，还会给出原因：

<Image src={imgSessionRunsOn} alt="会话详情：“运行于”显示服务中的成员，原因为“负载最低”" width={300} />

| 原因 | 含义 |
| --- | --- |
| **未加入组** | Agent 分配在单台 Daemon 上，而不是组上。 |
| **未开启分散** | 组的**在组内分散会话**开关未开启。 |
| **共享工作区** | 该会话使用 Agent 的共享工作区，而非独立会话工作区。 |
| **负载最低** | 服务成员相对于自身容量已经是当前最空闲的机器。 |
| **没有成员能运行** | 没有开启共享的成员满足该会话的运行条件。 |
| **成员均已满** | 所有开启共享的成员都已达到并发会话上限。 |
| **控制面不可达** | 创建会话时无法与控制平面通信以决定调度位置。 |

### 如果共享机器离线 [#if-a-lending-machine-goes-away]

调度到另一台机器上的会话会一直绑定在那台机器上。如果该机器短暂离线，会话轮次会返回可重试错误；如果离线超过约 10 分钟，会话会在其他成员上重新启动，原机器上尚未提交的工作不会保留。

## 限制 [#limitations]

- 故障转移后不会自动重新平衡 Agent，恢复上线的旧成员也不会自动拿回原先服务的 Agent。
- 未配置共享 PostgreSQL 存储时，对话历史不会随 Agent 迁移到新成员。
- 共享容量的机器必须运行 Linux、能够直接互通，并在防火墙中放行随机监听端口。
- 多网卡机器会通告其连接 AgentConnect 时所使用的地址，目前暂不支持手动覆盖。
