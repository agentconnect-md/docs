通过 Gitea 集成，你可以让 Agent **监视一个仓库**。新的 Issue、Pull Request、评论和已提交的评审会自动开启会话，Agent 也会以评论、正式评审和提交状态的形式回复。这套机制在 **gitea.com** 和**自托管实例**上的行为完全一致。同一个部署只能连接其中之一，不能同时连接两者。

与 GitHub（通过安装在组织上的 App 行事）和 GitLab（为每个 Agent 创建独立服务账号）不同，Gitea 采用**每个组织一个机器人用户**的模式。所有 Agent 在 Gitea 上的操作（克隆、推送、评论、评审和上报提交状态）都归属于这个机器人用户，它的个人访问令牌是 AgentConnect 保存的唯一 Gitea 凭证。

需要 Gitea **1.23 或更高版本**，或 Forgejo **15 或更高版本**。Forgejo 实例（包括 Codeberg）与 Gitea 完全兼容：API、令牌和 Webhook 都一致，本页所有说明同样适用于 Forgejo。

## 连接 Gitea [#connect-gitea]

每个组织只需在**集成 → 代码托管平台 → Gitea → 连接 Gitea** 中连接一次，粘贴你创建的机器人用户的个人访问令牌即可。

1. 在实例上创建一个**专用的机器人用户**。不要使用个人账号，也不要设为实例管理员（管理员会被识别为所有仓库的所有者，导致下文的权限检查失效）。
2. 以该机器人用户登录，进入 **Settings → Applications → Manage Access Tokens**。
3. 生成一个包含以下四个权限范围的令牌：

   | 权限范围            | 用途                                               |
   | ------------------- | -------------------------------------------------- |
   | `read:user`         | 读取机器人自身身份及其所属组织。                   |
   | `write:repository`  | 管理 Webhook、提交状态、评审以及读取仓库内容。     |
   | `write:issue`       | 在 Issue 和 Pull Request 上发表评论和添加表情回应。 |
   | `read:organization` | 为仓库选择器列出组织下的仓库。                     |

4. 将令牌粘贴到卡片中。在保存之前，AgentConnect 会核验机器人身份、最低版本要求以及上述四个权限范围。如果该机器人用户已经绑定了此部署下的其他组织，令牌也会被拒绝。

令牌在静态存储时经过加密，不会通过任何 API 返回，只会在 Daemon 的已认证连接上以短期租约的形式下发。由于令牌拥有机器人用户的完整权限，在已连接仓库中工作的 Agent 可以执行该机器人在该仓库内允许的一切操作。因此，请通过**控制机器人拥有哪些仓库的管理权限**来划分边界，而不是试图拆分令牌。

每个组织只能有一个 Gitea 连接。如果需要更换为其他机器人用户，请先断开连接再重新连接；使用替换令牌只会保留同一个机器人用户。

## 在每个仓库上给机器人 Admin 权限 [#give-the-bot-admin-on-each-repository]

AgentConnect 会自动安装、修复、测试和删除每个仓库的 Webhook，而 Gitea 的 Webhook 接口要求仓库 **Admin** 权限。请为所有需要 Agent 参与的仓库授予机器人 **Admin** 权限：

- 按仓库授权：进入 **Settings → Collaborators → Add collaborator**，将权限设为 **Administrator**。
- 按组织授权：创建一个具备 **Administrator** 单元权限的团队，并将机器人加入该团队。

查询贡献者权限同样需要 Admin 权限，因为 Gitea 只允许仓库管理员查询其他用户的权限级别。

## 使用中的仓库 [#repositories-in-use]

连接完成后，仓库会在首次被使用时自动登记到组织中：无论是被**触发器**选中、设为 Agent 的**工作区**，还是添加为 Agent 的**其他仓库**，AgentConnect 都会在保存时自动记录该仓库，并在 Gitea 卡片上显示为**就绪**。各个选择器都会列出机器人**当前拥有管理权限**的仓库，尚未使用的仓库会标注为*保存时添加*。如果某个仓库没有出现在列表中，请先在 Gitea 中为机器人授予该仓库的 Admin 权限。

托管 Webhook 会在为该仓库创建第一个已启用的触发器时单独安装。触发器保存完成后，AgentConnect 会立即按触发器监听的事件安装 Webhook、发送一次测试投递，并在 Relay 收到测试请求后清除该行的警告。仅作为工作区或其他仓库使用的仓库不需要 Webhook，在被触发器使用前也不会显示 Webhook 状态。

你也可以提前点击 Gitea 卡片上的**添加仓库**来登记仓库。这一步是可选的，同样不会安装 Webhook，直到添加第一个已启用的触发器时才会安装。

多个 Agent 可以共用同一个仓库及其 Webhook。该 Webhook 会订阅所有相关触发器监听事件的并集，并在触发器或 Agent 被移除时自动收窄事件范围。删除最后一个触发器后，仓库仍会保留在卡片上（不带 Webhook），直到你手动点击**移除**。

每一行仓库都会显示当前状态及可用操作：

| 状态                 | 含义                                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **正在设置**         | 正在执行初始化配置。                                                                                                     |
| **就绪**             | 仓库已登记且已确认机器人的 Admin 权限。如果有触发器需要 Webhook，也会在此完成安装与验证；如果测试投递未到达，会显示警告。 |
| **设置未完成**       | 机器人失去了 Admin 权限。现有会话仍可运行（评论、评审、提交状态和 Git 操作只需 Write 权限），但 Webhook 修复会停止，贡献者权限检查一律按无权限处理。 |
| **机器人访问已降级** | Gitea 拒绝了机器人令牌。请在连接上替换令牌，然后点击**修复**。                                                           |
| **移除未完成**       | 移除过程未完成，Webhook 可能仍残留在仓库上。                                                                             |

- **修复**：重新运行配置流程。适用于 Webhook 被手动删除，或已根据状态提示修复问题后的恢复。
- **轮换 Webhook 签名密钥**：安装一个新的替换 Webhook，待 Gitea 使用新密钥成功投递事件后，再停用旧的 Webhook。
- **移除**：删除 Gitea 上的托管 Webhook，让 Agent 停止在该仓库响应，但不会改动仓库的代码或历史记录。只要还有触发器、Agent 工作区或其他仓库引用了该仓库，移除会被阻止并列出具体引用项，请先清理这些引用。

如果测试投递一直没有到达，仓库状态会保持**就绪**并提示检查出站 Webhook 允许列表，帮助你在配置阶段就发现网络拦截问题，而不是等到漏掉第一个 Pull Request 才察觉。自托管实例的详细说明见 [AgentConnect OSS 上的 Gitea](/self-hosting/provider-apps#gitea)。

## 监视仓库 [#watch-a-repository]

在 Agent 页面，进入**集成 → 添加集成 → Gitea**。

<Image src={imgGiteaAddIntegration} alt="选择了 Gitea 的添加集成对话框：选择仓库、事件类型和触发条件" width={560} />

触发器依赖已有授权，不会自动新建仓库授权。目标仓库必须已经是该 Agent 的[工作区](/build-your-team/agents/workspaces-and-repos)或已授权的其他仓库，否则添加监视项会被拒绝。仓库不需要提前出现在 Gitea 卡片上，把它设为工作区或其他仓库时会自动完成登记。

选择仓库、监听对象（**Issue**、**Pull Request**、**Release** 或任意组合），以及触发条件：

- **创建时**：当 Issue 或 Pull Request 创建时触发，以及之后在同类型讨论中被明确提及时触发。
- **任意更新**：在创建的基础上，还包括新提交修订、回复和已提交的评审。关闭、重新打开和合并不会触发 Agent。
- **@ 提及**：当有人 @ 提及该 Agent（`@<agent-name>` 或 `@<organization>/<agent-name>`）或组织的 Gitea 机器人时触发。无论触发节奏如何设置，将机器人指定为评审者都会启动一轮任务。

对于 Release，当 Release **已发布**或发生**任意更新**（每次发布或编辑）时会运行 Agent。

如果多个 Agent 同时监视同一个仓库，可以在 Issue 或 Pull Request 这一行点击**添加决策**，通过[决策](/build-your-team/decisions#pick-agents-for-issues-and-pull-requests)决定由哪些 Agent 处理对应事件。

<Image src={imgGiteaAgentCard} alt="一个 Agent 的 Gitea 卡片，显示一个被监视的仓库及其 Pull Request 和 Issue 触发条件" width={640} />

多个 Agent 可以同时监视同一个仓库。`@<agent-name>` 只会触发对应的单个 Agent，提及机器人自身的用户名则会广播给所有匹配的 Agent。

<Image src={imgGiteaIssueReplies} alt="同一个 Issue 通过一个 Webhook 由两个 Agent 回复：每条评论均由机器人用户发出，并注明对应的 Agent" width={720} />

在组织名下的仓库中，`@<organization>/<agent-name>` 同样可以精准触发单个 Agent。在 Gitea 评论框中输入 `@` 时会自动补全组织团队，但不会提示 Agent 名称。你可以创建一个与 Agent 完全同名的团队（例如 `review-bot`，而不是“Review Bot”），让这个定向提及出现在自动补全中。Gitea 会向组织所有者和站点管理员展示所有团队，但对其他成员只展示其所在的团队，因此需要把使用该快捷方式的同事加为团队成员。

团队成员关系不影响实际触发逻辑：AgentConnect 只匹配输入的文本，不检查团队成员。无论团队是否存在，手动输入 `@<organization>/<agent-name>` 和直接输入 `@<agent-name>` 都照常生效。由于团队只存在于组织中，个人账号名下的仓库无法自动补全，直接使用 `@<agent-name>` 即可。

因为 Gitea 的 Issue 和 Pull Request 共用一套编号，会话会同时以事件类型和编号作为键，所以 Issue 12 和 Pull Request 12 始终是两个独立的会话。

### Gitea 评论中的评审 [#reviews-in-a-gitea-comment]

当评审提交时，Gitea 只会发送一个包含评审摘要的 Webhook 事件，不附带行内评论的文件路径、行号或正文。AgentConnect 会在构造提示词前通过 Gitea API 拉取该评审下的所有行内评论，确保 Agent 看到完整上下文。在正式评审之外单独留下的行内评论在 Gitea 上不会产生 Webhook 事件，因此也无法为此配置触发器。

## 谁可以触发 Agent [#who-may-trigger-an-agent]

事件到达时，AgentConnect 会通过 Gitea API 实时检查内容作者的**当前仓库权限**。只有具备 **Write 及以上**权限的用户才能触发 Agent。权限不足、缺失或无法验证时，一律按无权限处理，不会启动 Agent。

来自 fork 的 Pull Request 不会自动启动 Agent。当前拥有 Write 及以上权限的协作者可以通过提及 Agent，或将机器人指定为评审者来发起首轮任务。如果要让 Write 以下权限的用户也能触发 Agent，请在监视项设置中将他们加入**受信任用户**。该列表的规则与 [GitHub](/connect-automate/triggers-automation/github#trusted-users) 相同，也是 Write 以下用户触发 Agent 的唯一途径。触发权限与 Agent 后续的操作权限相互独立：发表评论、提交评审和推送代码仍然取决于授予该 Agent 的仓库授权。

机器人用户自身的操作不会触发 Agent，但有一个例外：机器人开启的 Pull Request 仍可进入评审流程，从而让一个 Agent 可以评审另一个 Agent 的工作。

## Agent 会做什么 [#what-the-agent-does]

每个符合条件的事件都会在 Agent 所在的 Daemon 上启动一个会话，并将事件信息作为上下文传入。这些会话会出现在[会话](/operate-govern/sessions)列表中，并链接回 Gitea。

- **普通回复**：由机器人用户在 Issue 或 Pull Request 上发表评论。在回复发出前，AgentConnect 会先在触发评论上添加 `eyes` 表情回应，表示已收到请求。
- **评审**：在 Pull Request 监视项中展开 **PR 评审**，可启用带行内评论的正式 `COMMENT` 评审、`REQUEST_CHANGES` 和 `APPROVE`。Gitea 只支持**按单行发表评论**，不支持多行范围；多行范围会折叠到结束行，并在评论第一行注明起始行号。
- **运行状态**：在 Pull Request 的 head 提交上上报一条 context 为 `agentconnect/<agent-name>` 的提交状态，链接回控制台里的会话。除非你将该 context 加入分支保护的必需检查，否则它不会阻止合并。

<Image src={imgGiteaPrReview} alt="机器人用户在 Pull Request 上提交的 REQUEST_CHANGES 评审：包含摘要以及锚定到具体代码行的行内评论" width={800} />

如果想让 Agent 在某个 Pull Request 上再次运行，可以在讨论中发送后续评论、推送新提交，或重新请求机器人作为评审者。

Git 通过 Daemon 的[凭证代理](/operate-govern/sandboxing/credential-protection#code-host-credentials)访问 Gitea，因此**机器人令牌不会进入 Agent 会话**。此外没有专门的 Gitea 命令行封装，Agent 通过 AgentConnect 提供的代码托管平台工具执行读写操作。

## Gitea 拒绝的操作 [#what-gitea-refuses]

Gitea 不允许 Pull Request 的作者批准自己的 PR 或请求修改。当 PR 是由机器人自己创建时（例如一个 Agent 评审另一个 Agent 开的 PR），Gitea 不会接受批准或请求修改的结论。遇到这种情况，AgentConnect 会将相同的评审内容改以普通评审评论发布，并在会话中说明这次降级，保证所有评审意见完整保留。

另外，`COMMENT` 评审不会覆盖之前的 `REQUEST_CHANGES` 结论。只有当该评审者重新提交批准或拒绝时，Gitea 才会更新其评审结论。

## 替换令牌 [#replace-the-token]

Gitea 的访问令牌没有过期时间，而且在没有用户密码的情况下无法由应用创建或撤销，因此 AgentConnect 无法自动轮换令牌。如需在控制台更换令牌，请点击连接上的**替换令牌**。该操作会执行与首次连接相同的校验，要求令牌属于**同一个机器人用户**，并原子地切换存储的密钥，同时清除 Daemon 缓存中的旧令牌。

**请手动在 Gitea 中撤销旧令牌**，AgentConnect 无法代为撤销。由于令牌没有到期日，系统无法提前预警；只有在 Gitea 拒绝请求时，AgentConnect 才会检测到令牌失效，并将该连接下的所有仓库标记为**机器人访问已降级**，直到你完成替换。

## 断开连接 [#disconnect]

点击**断开连接**会先删除 Gitea 上所有的托管 Webhook，再释放连接，Agent 随后停止在这些仓库响应。断开后请记得前往 Gitea 撤销对应的访问令牌。

如果令牌已经失效或被撤销，部分仓库可能会停留在**移除未完成**状态，其 Webhook 仍留在 Gitea 上。你可以先替换令牌再重新执行移除，或直接到 Gitea 手动删除该 Webhook。

## 自托管实例 [#self-hosted-instances]

上述功能在自托管实例上的使用方式完全相同。每个部署只需完成一次运维配置：将部署指向你的实例，并确保实例满足前提条件（Gitea 1.23+ 或 Forgejo 15+、单个 HTTPS 地址、受信任证书，以及允许 Gitea 访问部署的出站 Webhook 允许列表）。完整配置见 [AgentConnect OSS 上的 Gitea](/self-hosting/provider-apps#gitea)。

**不需要注册 OAuth 应用**。Gitea 的 OAuth 令牌不会生成独立的机器人身份（使用 OAuth 令牌执行的操作同样归属于授权用户，与个人访问令牌无异），因此机器人用户及其个人访问令牌就是完整的身份。

一旦产生 Gitea 相关数据，实例地址就无法更改。已保存的令牌、数字仓库 ID 和 Webhook ID 都不包含实例标识，修改地址会导致凭证被发往错误实例。Daemon 上不需要额外配置实例信息，它会自动从所服务的 Agent 获取相关设置。
