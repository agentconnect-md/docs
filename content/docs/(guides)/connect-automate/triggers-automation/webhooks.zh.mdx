Webhook 集成会为 Agent 提供一个**入站 HTTPS 端点**。任何能够发送 JSON POST 请求的系统（如 CI 流水线、监控告警、其他机器上的定时任务或你自己的应用）都可以触发该 Agent。

<Image src={imgWebhookIntegration} alt="Webhook 表单：名称、会话连续性、指令和 HMAC 签名" width={640} />

## 创建 [#create-one]

在 Agent 页面中打开**集成 → 添加集成 → Webhook**，然后配置以下选项：

- **名称**：默认为 `<agent>-webhook`。
- **会话连续性**：决定哪些投递共用同一个会话（详见[会话](#sessions)）。
- **指令**：可选，用于指定 Agent 收到投递后的处理方式。如果由发送方自行传入消息内容，留空即可；如果接入的是无法修改请求格式的现有系统，请在此填写固定指令（详见[两种告诉 Agent 做什么的方式](#two-ways-to-tell-the-agent-what-to-do)）。
- **要求 HMAC 签名**：可选，在端点 URL 之外额外启用签名密钥校验。

点击**创建**后，对话框会显示：

- **入站端点**：该集成的 `POST` URL。URL 中的令牌即为凭据，请妥善保密。
- **签名密钥**：仅在启用签名校验时显示，且**只显示一次**，请立即复制保存。
- **发送测试投递**：一条可直接使用的 curl 命令，支持编辑测试消息，方便你在写代码前先验证连通性。

如需修改指令，点击 Agent 的**集成**卡片中对应 Webhook 一行的铅笔图标即可。

## 两种告诉 Agent 做什么的方式 [#two-ways-to-tell-the-agent-what-to-do]

**由发送方写消息。** 将**指令**留空。Agent 会按顺序取请求体中第一个存在的 `prompt`、`text` 或 `message` 字符串字段作为指令，将其余字段作为上下文一并传入；如果这三个字段都不存在，则将整个请求体原样交给 Agent。这种方式适合由你控制请求格式的场景，例如 CI 步骤、脚本或自研应用。建议将指令字段放在大段日志或诊断数据之前：

```bash
curl -X POST "$WEBHOOK_URL" \
  -H "content-type: application/json" \
  -d '{"message":"Deploy of api-server v2.31 failed on step migrate — investigate and summarize.","log_url":"https://ci.example.test/runs/1234"}'
```

**由 Webhook 自带指令。** 填写**指令**，例如*“分析这条告警：在服务最近的变更里找出可能原因，并发一段简短总结。”* 之后每次投递都会将这段指令连同完整请求体一起传给 Agent，且 Agent 会将请求体严格当作数据而非指令处理，不会从中提取特定字段。这种方式适合直接接入格式固定的第三方系统（如告警工具、错误追踪或表单服务）。由于这类系统转发的内容（错误信息、告警描述等）可能来自外部用户输入，在 Webhook 上配置固定指令可以防止请求体内容被当作指令执行。

指令最多支持 8,000 个字符。无论采用哪种方式，Agent 自身的描述都会继续生效。

## 签名请求 [#sign-requests]

开启**要求 HMAC 签名**后，每个请求都必须对原始请求体使用签名密钥计算 HMAC-SHA256，并通过请求头 `X-AC-Signature: sha256=<hex>` 发送：

```bash
BODY='{"message":"Nightly import finished with 3 rejected rows — summarize them."}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$WEBHOOK_SECRET" -r | cut -d' ' -f1)

curl -X POST "$WEBHOOK_URL" \
  -H "content-type: application/json" \
  -H "X-AC-Signature: sha256=$SIG" \
  -d "$BODY"
```

缺少签名或签名错误的请求，会按未知 URL 一样被拒绝。

## 会话 [#sessions]

**会话连续性**决定 Agent 将哪些投递归入同一个上下文：

- **每次投递新建会话**（默认）：每次 POST 请求都会开启一个独立会话。
- **每个主题一个会话**：携带相同 `X-AC-Session-Key` 请求头的投递会延续同一个会话，让同一张工单、同一笔订单或同一段对话在多次事件间持续积累上下文。未携带该请求头的投递则会各自开启新会话。
- **整个 Webhook 共用一个会话**：所有投递都延续同一个会话。

每次触发产生的会话都会显示在[会话](/operate-govern/sessions)中，触发来源标注为该 Webhook，并保留完整记录。Agent 页面中对应 Webhook 一行会显示最近触发时间，点击历史按钮即可查看近期投递记录、执行结果及对应会话。

## 请求参考 [#request-reference]

| | |
| --- | --- |
| 方法和类型 | `POST`，`content-type: application/json` |
| 请求体大小 | 最大 128 KiB。Agent 会读取前 64 KiB，请求体被截断时会收到提示。 |
| `X-AC-Delivery-Key` | 可选，最多 200 个字符。用于标识单次投递：使用相同键重试时会自动去重，不会重复执行。未提供时由系统自动生成。 |
| `X-AC-Session-Key` | 可选，最多 200 个字符。当 Webhook 使用**每个主题一个会话**时，用于将投递归入同一个会话。 |
| `X-AC-Signature` | `sha256=<hex>`。仅在 Webhook 启用签名校验时必需。 |
| `202` | 已接收。响应体为 `{"deliveryKey":"…"}`，Agent 会在返回响应后开始运行。 |
| `404` | 未知 URL，或签名缺失、错误。 |
| `429` | 该 Webhook 投递频率过高（支持 10 次突发，之后约每秒 1 次）。稍后使用相同的投递键重试即可。 |

## 提示 [#tips]

- 将 Webhook 与 [GitHub 工作区](/build-your-team/agents/workspaces-and-repos)搭配使用，让 Agent 能够直接查看请求中涉及的代码。
- 如需轮换 URL 和签名密钥，删除当前 Webhook 集成后重新创建一个即可。编辑 Webhook 不会更改其 URL。
