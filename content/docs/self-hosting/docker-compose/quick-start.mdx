The Docker Compose stack runs AgentConnect on a single machine for local evaluation, with daemons on machines you operate. For a cluster deployment, see [Deploy with Helm](/self-hosting/kubernetes/deploy).

## Before you start

You need:

- Docker Desktop, OrbStack, or Docker Engine
- Docker Compose v2 (`docker compose version`)
- Git

Published AgentConnect images currently target `linux/amd64`. Docker Desktop and OrbStack can run them under emulation on Apple Silicon.

## 1. Start the stack

```bash
git clone https://github.com/agentconnect-md/agentconnect.git
cd agentconnect
docker compose up -d --pull always
```

To build images from your local checkout instead of pulling published ones, run `docker compose up -d --build`. Every service in `compose.yaml` includes a build definition, and the built images use the tags already referenced by the stack. Builds target `linux/amd64` like the published images, so they run under emulation and are slower on Apple Silicon.

The first run starts PostgreSQL 18, applies the database migrations, initializes the local no-auth organization, and starts the application services. It doesn't add sample data. The built-in `agentconnect` agent is enabled by default and can be disabled in [Setup](/self-hosting/docker-compose/configuration#setup-server).

Check the stack:

```bash
docker compose ps --all
```

`postgres`, `control-plane`, `relay`, `setup-server`, and `web` should be running. `migration-files` and `migrate` are one-shot jobs and should show `Exited (0)`.

## 2. Open AgentConnect

Open [http://localhost:3000](http://localhost:3000).

By default, the stack binds its ports to `127.0.0.1` with sign-in disabled. Use this mode locally only.

You can check the service health probes directly:

```bash
curl http://localhost:8080/readyz
curl http://localhost:8090/readyz
```

## 3. Connect a daemon

The Compose stack doesn't run the daemon in a container. Running it on the host gives agents access to local repositories, runtime launchers, and your existing Claude or Codex authentication.

In the Web console:

1. Open **Infra** and choose **Add daemon**.
2. Copy the one-time command.
3. Run that exact command on the machine that will host the agents.

The daemon connects to the Control Plane and Relay over outbound connections. If it runs on another machine, configure host-reachable URLs first. See [Network and public URLs](/self-hosting/docker-compose/configuration#network-and-public-urls).

## Guided setup

Once you move past the local stack to sign-in, public URLs, provider apps, and production hardening, you can use the bundled setup skill instead of doing everything by hand. The repository includes it at `.claude/skills/agentconnect-setup` and exposes it under `.agents/skills` so Claude Code, Codex, and other agent harnesses detect it automatically.

Open your coding agent in the checkout and ask it to set up AgentConnect. It walks through this page and the deployment guides interactively, verifying each checkpoint before continuing, and won't ask you to paste secrets into chat.

The sections below cover the same steps manually and remain the reference whether or not you use the skill.

## Optional: add local sign-in

The repository includes a Logto OSS overlay for testing real sign-in without setting up DNS or TLS:

```bash
docker compose -f compose.yaml -f compose.logto.yaml up -d
```

Then open:

- Setup: [http://localhost:8091](http://localhost:8091)
- Logto Console: [http://localhost:3002](http://localhost:3002)
- AgentConnect: [http://localhost:3000](http://localhost:3000)

Continue with [Sign-in](/self-hosting/sign-in). Google is the quickest local sign-in option. The local overlay uses a separate Logto database in the same PostgreSQL service and stays bound to loopback.

When using the overlay, include both `-f` flags in later `up`, `pull`, and `down` commands.

For hosted production sign-in, skip the overlay and connect a [Logto Cloud tenant](/self-hosting/sign-in#logto-cloud) instead.

## Logs and updates

Follow the stack logs:

```bash
docker compose logs -f
```

Pull the latest images and apply migrations:

```bash
docker compose pull
docker compose up -d
```

If you created `compose.env`, pass `--env-file compose.env` to each command. Pin `AGENTCONNECT_VERSION` to a release tag for reproducible deployments.

## Stop or reset

Stop the stack while keeping its database:

```bash
docker compose down
```

Delete the database and start fresh:

```bash
docker compose down --volumes
```

> This permanently deletes Control Plane and Setup Server data in the Compose database. Daemon-local workspaces and transcripts live outside this volume and aren't deleted.

## What the stack includes

| Component | Location | Purpose |
| --- | --- | --- |
| Web console | Docker | Configure and follow work |
| Control Plane | Docker | Auth and coordination data |
| Relay | Docker | Public callback ingress |
| Setup Server | Docker, loopback only | Configure deployment auth and providers |
| PostgreSQL | Docker | Persist deployment and Control Plane data |
| Logto OSS | Optional overlay | Local sign-in |
| Object store (RustFS) | HTTPS overlay | File uploads and large workspace downloads ([File transfer](/self-hosting/docker-compose/configuration#file-transfer-and-the-object-store)) |
| Daemon | Host or another machine | Run agents and store local data |

The Relay is included so GitHub, webhooks, webchat, and HTTP bot callbacks work without changing the stack. Direct Slack Socket Mode, Telegram, Discord, and Lark / Feishu connections still run directly between the daemon and their providers.

## Deployment boundary

The bundled Compose topology is meant for local evaluation and single-host deployments. Before exposing it on a network, configure real sign-in, replace the default secrets, enable TLS, back up PostgreSQL, and configure WebSocket support on your reverse proxy.
