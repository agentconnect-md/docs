官方 AgentConnect Helm Chart 是生产环境推荐的 OSS 部署方式。它会部署 Web 控制台、控制平面、Setup Server、Relay、连接器网关，以及一个集群级 Daemon 池。Agent Runtime 运行在带持久化工作区的隔离 `agent-sandbox` Pod 中，不再依赖运维人员的本地机器。

如果只是做本地评估，请先看 [Docker Compose 快速开始](/self-hosting/docker-compose/quick-start)。当你需要由集群统一管理 Agent 执行和工作区时，使用本指南。

该 Chart 以 OCI 制品的形式发布在 `oci://ghcr.io/agentconnect-md/charts/agentconnect`。版本号与 AgentConnect 发布版本一致（不含前导 `v`），默认拉取的镜像标签也对应同一版本。

## 开始之前 [#before-you-start]

请先准备：

- Kubernetes 1.28 或更新版本
- 集群的 Helm 和 `kubectl` 访问权限
- `linux/amd64` 架构的工作节点（当前官方镜像仅支持该架构）
- 一个能从 AgentConnect 命名空间访问的 PostgreSQL 数据库
- 用于 Agent 工作区的动态卷供应器和 StorageClass
- 安装 CRD、集群级 RBAC 和 `agent-sandbox` 控制器的权限
- 如需对外开放访问：一个 Gateway API 控制器、现成的 Gateway、DNS 和 TLS 证书

Chart 会创建 `HTTPRoute` 资源，但不负责安装 Gateway API 控制器、创建 Gateway，也不管理 DNS 和证书。你也可以设置 `route.enabled: false`，自行配置入口。

先到 [AgentConnect 发布页](https://github.com/agentconnect-md/agentconnect/releases)选择一个包含该 Chart 的版本（`v1.44.0-rc.58` 及以上），然后验证制品。注意版本号不要带前导 `v`：

```bash
export AGENTCONNECT_CHART_VERSION=X.Y.Z

helm show chart oci://ghcr.io/agentconnect-md/charts/agentconnect \
  --version "$AGENTCONNECT_CHART_VERSION"
```

所有受支持的配置项都记录在 Chart 的 [values.yaml](https://github.com/agentconnect-md/agentconnect/blob/main/charts/agentconnect/values.yaml) 中。

## 1. 创建命名空间和 Secret [#1-create-the-namespace-and-secrets]

创建 Release 命名空间：

```bash
kubectl create namespace agentconnect
```

控制平面需要 PostgreSQL 连接串、长期稳定的 API 密钥 pepper，以及共享的 Relay 凭证：

```bash
kubectl -n agentconnect create secret generic agentconnect-secrets \
  --from-literal=DATABASE_URL='postgresql://control_plane:replace-me@postgres.example.test:5432/agentconnect?schema=public' \
  --from-literal=API_KEY_PEPPER="$(openssl rand -hex 32)" \
  --from-literal=RELAY_TOKEN="$(openssl rand -hex 24)" \
  --from-literal=OPEN_CONNECTOR_ENCRYPTION_KEY="$(openssl rand -hex 32)"
```

`API_KEY_PEPPER` 一经设定就不应随意改动：轮换它会让现有的 Daemon 密钥和个人 API 密钥全部失效。连接器加密密钥用于加密持久卷里的连接器 OAuth 凭证，应在创建第一个连接前设置好。请把这些值妥善存放在密钥管理器中，数据库密码需做 URL 编码。

Kubernetes Daemon 池需要一份单独的数据平面配置文件，用来持久保存池成员共享的会话、会话记录、队列等执行数据。将以下内容保存为 `data-plane.json`：

```json
{
  "version": 1,
  "databaseUrl": "postgresql://daemon_pool:replace-me@postgres.example.test:5432/agentconnect",
  "maxConnections": 4
}
```

用这个文件创建 Secret：

```bash
kubectl -n agentconnect create secret generic agentconnect-data-plane \
  --from-file=config.json=./data-plane.json
```

控制平面和 Daemon 池可以共用同一个 PostgreSQL 实例，但建议各自使用独立的数据库凭证，方便分别控制权限和轮换，并同时备份控制数据和执行数据。

## 2. 创建 values 文件 [#2-create-the-values-file]

建议只写一个精简的覆盖文件，不要整份复制 Chart 默认值。将下面的内容保存为 `agentconnect-values.yaml`，按实际环境替换域名、Gateway 监听器和 StorageClass：

```yaml
publicUrl: https://app.example.test

# Configure this before the first install so Setup uses the intended issuer and Management API.
logto:
  endpoint: https://login.example.test
  # Set this separately when a custom login domain does not serve the Management API.
  mgmtEndpoint: https://tenant.example.test

route:
  # Keep the deployment private until Logto sign-in is configured.
  enabled: false
  gateway:
    name: public-gateway
    namespace: default
    sectionName: https

daemonPool:
  # The chart creates this namespace with restricted Pod Security labels and default-deny networking.
  sandboxNamespace: agentconnect-agents
  runtime:
    workspace:
      storageClass: standard
      size: 10Gi

# The default-on connector gateway persists its own SQLite database in a separate PVC.
openConnector:
  persistence:
    storageClass: standard
```

`publicUrl` 是最终的浏览器访问地址。在默认同源拓扑下，控制台挂在 `/`，控制平面挂在 `/cp`，Relay 路径也复用同一主机名。如果需要独立的公开域名，Chart 也支持分别配置 `apiHost`、`mcpHost` 和 `relay.host`。

Daemon 池默认启动三个成员，并预热三个 Runtime 沙箱。每个预热沙箱都会常驻一个 Pod 和一块工作区 PVC。如果更看重控制常驻成本而不是首次启动速度，可以把 `daemonPool.runtime.warmReplicas` 设为 `0`。

默认 Runtime 镜像内置了 Claude Code、Codex、DeepSeek Harness 和 OpenCode。如果要使用包含 Qwen Code 及其他 ACP Runtime 的完整镜像，请参阅 [Runtime 认证](/self-hosting/kubernetes/runtime-authentication#choose-the-runtime-image)。

### 在集群内运行 Logto [#run-logto-in-the-cluster]

Chart 本身不部署 Logto。无论使用 [Logto Cloud](/self-hosting/sign-in#logto-cloud) 还是在集群内自建 Logto，AgentConnect 在启动配置里只需要上面的两个 `logto` 字段，其余登录配置都在 Setup Server 中完成。

如果 Logto 运行在集群内，`endpoint` 填面向浏览器的公开地址，`mgmtEndpoint` 填集群内的 Service 地址：

```yaml
logto:
  endpoint: https://login.example.test
  mgmtEndpoint: http://logto.agentconnect.svc.cluster.local
```

要让这套配置正常工作，有三个关键点：

- **用 80 端口的 Service 代理 Logto 容器端口。** Logto 会根据收到的请求构造对外发布的 URL，如果集群内地址带显式端口号，这个端口会被写进 OIDC 发现响应里。把 Service 暴露在 80 端口并指向容器端口，就能让 `mgmtEndpoint` 不带端口，对外公布的 URL 也与公开地址保持一致。
- **为 Logto 开启 `TRUST_PROXY_HEADER`，并透传 `X-Forwarded-Proto: https`。** 如果 TLS 在 Gateway 之前终止，进入集群的这一跳会变成明文 HTTP。缺少该请求头时，Logto 会把签发者地址公布为 `http://`，导致所有 OIDC 发现请求失败。在 Gateway API 中可以通过路由上的 `RequestHeaderModifier` 过滤器补上这个头。
- **不要为 Logto 管理控制台配置公网路由。** 和 Setup Server 一样，通过 `kubectl port-forward` 访问它，并把它的管理端点设为对应的本地地址。

无论怎么部署 Logto，Management API 的资源标识符始终是固定值 `https://default.logto.app/api`。它只是一个标识符，不是需要对外提供服务的 URL。

### 加密已存储的应用密钥 [#encrypt-stored-application-secrets]

默认情况下，只写的提供方密钥和 Agent 密钥会以明文存放在 PostgreSQL 中。在 Setup 或控制台里填入生产凭证之前，请先准备好 Vault Transit 密钥，以及绑定到 Chart 的 `agentconnect-control-plane` ServiceAccount 的 Kubernetes 认证角色，然后在 values 文件里加上加密配置：

```yaml
controlPlane:
  config:
    SECRET_CIPHER: vault-transit
    VAULT_ADDR: https://vault.example.test
    VAULT_TRANSIT_KEY: agentconnect-cp
    VAULT_JWT_ROLE: agentconnect
```

Setup Server 默认共用同一个 ServiceAccount 和这套加密配置，因此两个服务可以加解密同一批数据。Transit 策略写法和历史数据迁移步骤见[密钥存储](/self-hosting/docker-compose/configuration#secret-storage)。

### 为所有 Agent 提供模型凭证 [#model-credentials-for-every-agent]

关于 API 密钥配置、按 Runtime 区分的 Secret 映射以及网关端点，详见 [Runtime 认证](/self-hosting/kubernetes/runtime-authentication)。这套映射会同时用于 Daemon 池探测和 Agent 会话。

池里的 Agent 需要模型提供方凭证。如果按 Agent 或按组织分配，直接在控制台配置对应的[变量或密钥](/build-your-team/variables-and-secrets)即可（例如 `ANTHROPIC_API_KEY`、`OPENAI_API_KEY`、`DEEPSEEK_API_KEY`）。如果整个部署共用同一套模型密钥，可以放进一个 Secret 里，由 Chart 统一引用：

```bash
kubectl -n agentconnect create secret generic agentconnect-model-credentials \
  --from-literal=DEEPSEEK_MODEL_TOKEN='replace-me' \
  --from-literal=DEEPSEEK_MODEL_BASE_URL='https://api.deepseek.com'
```

```yaml
daemonPool:
  modelCredentials:
    existingSecret: agentconnect-model-credentials
```

Secret 中的**键名直接对应环境变量**：`<PREFIX>MODEL_TOKEN` 和 `<PREFIX>MODEL_BASE_URL`。前缀规则为：Claude 用 `ANTHROPIC_`，Codex 用 `OPENAI_`，DeepSeek 用 `DEEPSEEK_`，留空则作为共享回退项。OpenCode 会自动复用这三组提供方凭证，不需要额外映射。上面的示例用的是 [DeepSeek 文档中的 API 根地址](https://api-docs.deepseek.com/guides/harness/)。

只提供令牌、不填基础 URL 时，会直接请求对应提供方的默认端点。Agent Pod 里只会拿到占位符，真正的上游请求由 Daemon 池发起，因此 Daemon 池必须能通过 HTTPS 访问模型提供方（见 [Runtime 认证](/self-hosting/kubernetes/runtime-authentication#keys-stay-with-the-daemon-pool)）。只提供基础 URL、不填令牌时，Runtime 会连向自行签发凭证的端点。如果使用 Qwen Code 或其他 ACP Runtime，请参考 Runtime 认证指南，通过 `daemonPool.runtimeEnvironment` 映射它们各自的 API 密钥变量。

使用时需要注意两条规则：

- 这个 Secret 是部署里这些变量的**唯一**来源。如果在 `daemonPool.extraEnv` 里重复设置，或者同时让 `modelEgress.clients` 渲染同名变量，安装时会直接报错。令牌和基础 URL 必须成对来自同一来源，避免只含令牌的 Secret 和其他地方残留的基础 URL 混搭，把真实密钥发给错误端点。
- 出于同样原因，Secret 中的值**优先级高于 Agent 自身的同名变量**。如果你希望各个 Agent 使用自己的密钥，请不要配置 `modelCredentials`。

### 对象存储：Source Cache 与文件传输 [#object-store-source-cache-and-file-transfer]

接入兼容 S3 的对象存储后，会同时开启两项能力：

- **Source Cache**：新启动的沙箱会直接从对象存储里的 bundle 初始化 Git 仓库，不用每次都从源仓库完整克隆。沙箱 Pod 不会持有存储桶凭证，只拿到针对单个对象的短时签名链接。
- **控制台文件传输**：用户可以在 [Playground](/build-your-team/agents/playground#attach-files) 消息里附加任意文件，控制台也可以下载大文件或二进制工作区文件。文件字节直接在浏览器、Daemon（或其 Pod）和对象存储之间传输，控制平面只负责签发链接。集群外自托管的 Daemon 同样适用。

不配置对象存储时，这两项能力都处于关闭状态：克隆直接走源仓库，消息里只能附加图片，工作区下载则经由控制平面中转且单文件上限为 8 MiB。

#### 内置存储 [#bundled-store]

Chart 支持在单个 PersistentVolumeClaim 上运行一个 [RustFS](https://rustfs.com) Pod，只需指定一个公开主机名：

```yaml
sourceCache:
  store:
    host: objects.example.test
    persistence:
      size: 50Gi
      storageClass: standard
```

签名链接必须是 `https://`，所以对象存储需要通过 Gateway 在独立域名上暴露。请像配置 `publicUrl` 一样，为这个主机名准备好 DNS、TLS 和 Gateway 监听器。边缘代理必须保留 `Host` 请求头（所有签名都会校验该字段），并放宽请求体上限以容纳最大的 bundle（`sourceCache.limits.maxBundleBytes`，默认 `2Gi`）。只有在 `route.enabled` 为 `true` 时，Chart 才会为存储创建路由。

Chart 会在 `agentconnect-source-cache-store` Secret 中自动生成存储密钥对，并在升级时保留。一个 post-install / post-upgrade Job 负责创建存储桶、生命周期规则以及针对 `publicUrl` 的 CORS 规则，重复执行也是安全的。

在[第 4 步](#4-configure-sign-in-before-publishing-the-route)开启路由后，重启一次 Daemon 池，让成员马上识别到生命周期规则，而不用等下一次每 6 小时一次的检查：

```bash
kubectl -n agentconnect rollout restart deployment/agentconnect-daemon-pool
curl https://objects.example.test/health
```

#### 外部存储桶 [#external-bucket]

如果想使用自己的对象存储桶，设置 `sourceCache.enabled: true` 并填好地址和凭证。启用后会覆盖内置存储配置：

```yaml
sourceCache:
  enabled: true
  endpoint: https://s3.example.test
  # Set only when browsers and out-of-cluster daemons reach the bucket at another origin.
  publicEndpoint: ''
  region: us-east-1
  bucket: agentconnect-source-cache
  forcePathStyle: true
  credentials:
    source: secret
    secret:
      name: agentconnect-source-cache
```

该 Secret 应包含 `AWS_ACCESS_KEY_ID` 和 `AWS_SECRET_ACCESS_KEY`，并以文件形式挂载。在 EKS 上可以改用 `credentials.source: serviceAccount` 并指定 `roleArn`，该 IAM 角色需要同时信任 Daemon 池和控制平面的 ServiceAccount。使用 AWS 区域默认端点时，把 `endpoint` 留空即可。

Chart 和 AgentConnect 不会自动修改外部存储桶的配置，需要你手动补齐：

- **生命周期规则**（作用于 `<prefix>/src/`）：带 `ac-cache=pending` 标签的对象 2 天后过期，带 `ac-cache=unreferenced` 标签的对象 7 天后过期。未配置时，Daemon 池会停止写入 bundle，控制平面也会拒绝文件传输，两边都会在日志里打印出需要应用的规则 JSON。
- **CORS 规则**：允许 `publicUrl` 发起 `GET` 和 `PUT` 请求，并放行 `content-type`、`x-amz-checksum-sha256` 和 `x-amz-tagging` 请求头。
- **权限**：对 `<prefix>/src/*` 授予 `s3:GetObject`、`s3:PutObject`、`s3:DeleteObject` 和 `s3:PutObjectTagging`，对存储桶授予 `s3:GetLifecycleConfiguration`。

完整的生命周期规则、CORS 配置文档、AWS 和 MinIO 命令以及各项上限说明，见 Chart 的 [Source Cache 参考](https://github.com/agentconnect-md/agentconnect/blob/main/charts/agentconnect/README.md#source-cache)。

## 3. 安装 AgentConnect [#3-install-agentconnect]

安装前面校验过的版本：

```bash
helm upgrade --install agentconnect \
  oci://ghcr.io/agentconnect-md/charts/agentconnect \
  --version "$AGENTCONNECT_CHART_VERSION" \
  --namespace agentconnect \
  --values agentconnect-values.yaml \
  --wait \
  --timeout 15m
```

在全新集群上，Helm 会先安装四个 `agent-sandbox` CRD，Chart 随后安装对应版本的控制器栈，并创建专用的 agents 命名空间、Daemon 池的 TokenReview RBAC、SandboxTemplate 以及预热池。

检查发布状态：

```bash
kubectl -n agentconnect get pods
kubectl -n agentconnect-agents get pods,pvc
kubectl -n agentconnect logs deployment/agentconnect-control-plane -c migrate
```

确认迁移容器正常退出、各应用 Pod 变为 Ready，且 agents 命名空间里已经出现预热的沙箱 Pod 和 PVC。

## 4. 在发布路由之前配置登录 [#4-configure-sign-in-before-publishing-the-route]

Setup Server 默认不创建 Service，也不配公开路由。通过端口转发在本地访问它：

```bash
kubectl -n agentconnect port-forward deployment/agentconnect-setup-server 8091:8091
```

打开 [http://localhost:8091](http://localhost:8091)，连接 Logto，配置浏览器应用和第一个社交登录方式，并认领初始管理员。应用、API Resource 和提供方的详细配置步骤见[登录](/self-hosting/sign-in)。

前面提供的 values 文件已经把 Logto 端点传给了 Setup。如果 Logto Cloud 配置了自定义登录域名，请保持 `logto.endpoint` 指向自定义登录域名，`logto.mgmtEndpoint` 指向租户标准的 Management API 地址。

在 Setup 中保存配置后，需要重启启动时读取这些配置的服务。先重启控制平面，等它变为 Ready 后再重启 Web 和 Relay：

```bash
kubectl -n agentconnect rollout restart deployment/agentconnect-control-plane
kubectl -n agentconnect rollout status deployment/agentconnect-control-plane

kubectl -n agentconnect rollout restart \
  deployment/agentconnect-web \
  statefulset/agentconnect-relay
```

必须按这个顺序，是因为控制台会在启动时向控制平面拉取登录配置。如果和控制平面同时重启，控制台可能读到旧配置并缓存下来，导致页面上不显示登录按钮。等控制平面就绪后再重启就能避免；如果已经遇到，再重启一次控制台即可恢复。

等滚动更新完成后，把 `agentconnect-values.yaml` 中的 `route.enabled` 改为 `true`，再执行一次升级：

```bash
helm upgrade agentconnect \
  oci://ghcr.io/agentconnect-md/charts/agentconnect \
  --version "$AGENTCONNECT_CHART_VERSION" \
  --namespace agentconnect \
  --values agentconnect-values.yaml \
  --wait \
  --timeout 15m
```

确认路由已经正确绑定到目标 Gateway：

```bash
kubectl -n agentconnect get httproute
kubectl -n agentconnect describe httproute agentconnect
```

如果目标 Gateway 位于其他命名空间，它的监听器需要允许来自 AgentConnect 命名空间的路由。

## 5. 运行第一个 Agent [#5-run-the-first-agent]

打开最终的 Web 地址并登录。Daemon 池会自动注册为 **Kubernetes 集群**，不需要复制**添加 Daemon** 命令，也不用安装宿主机 CLI。

新建一个 Agent，运行环境选择 **Kubernetes 集群**，再从 Runtime 沙箱镜像上报的 Runtime 列表中选一个。给它配上对应的模型凭证：可以按 Agent 或组织配置[变量或密钥](/build-your-team/variables-and-secrets)，也可以按[为所有 Agent 提供模型凭证](#model-credentials-for-every-agent)做全局配置。然后在 Playground（控制台中显示为“试用”）里发一条消息，确认 Agent 成功拿到沙箱和持久化工作区。
