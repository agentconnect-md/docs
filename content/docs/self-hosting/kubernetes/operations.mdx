These tasks apply to a running Helm release. For initial installation, see [Deploy with Helm](/self-hosting/kubernetes/deploy).

## Upgrade

Back up PostgreSQL and important workspace PVCs, pick the new release, and read its release notes. Helm doesn't upgrade CRDs from a chart's `crds/` directory, so apply the version-matched CRDs before upgrading the controller and application workloads:

```bash
export AGENTCONNECT_NEW_CHART_VERSION=X.Y.Z
export AGENTCONNECT_CHART_DIR="$(mktemp -d)"

helm pull oci://ghcr.io/agentconnect-md/charts/agentconnect \
  --version "$AGENTCONNECT_NEW_CHART_VERSION" \
  --untar \
  --untardir "$AGENTCONNECT_CHART_DIR"

kubectl apply --server-side \
  -f "$AGENTCONNECT_CHART_DIR/agentconnect/crds/agent-sandbox.yaml"

helm upgrade agentconnect \
  oci://ghcr.io/agentconnect-md/charts/agentconnect \
  --version "$AGENTCONNECT_NEW_CHART_VERSION" \
  --namespace agentconnect \
  --values agentconnect-values.yaml \
  --wait \
  --timeout 15m
```

The chart version automatically selects matching application images. Leave `image.tag` and component tags empty unless you intentionally need a mixed-version deployment.

## Orphan cleanup

The daemon pool runs a scheduled reconciler for sandbox objects whose agents no longer exist. It defaults to dry-run mode. Review its summaries over an observation period before setting `daemonPool.reconciler.delete: true`, because deleting an orphaned sandbox claim also deletes its workspace PVC and can't be undone.

## Shared-cluster controller ownership

The `agent-sandbox` CRDs and controller are shared across the cluster. On a dedicated cluster, a single AgentConnect release can manage them. If multiple AgentConnect releases share one cluster, manage the CRDs and controller once outside those releases, install each chart with `--skip-crds`, and set `installCRD: false`. Don't let multiple Helm releases compete over the same cluster-scoped controller stack.

## Troubleshooting

- **A pod stays in `ContainerCreating`**: Run `kubectl describe pod`. Common causes are a missing `agentconnect-secrets` or `agentconnect-data-plane` Secret.
- **Daemon pool members never become Ready**: Check their logs and confirm the data-plane PostgreSQL URL, the `agent-sandbox` controller, and the runtime warm pool are healthy.
- **Sandbox pods stay Pending**: Check the configured StorageClass, node architecture, cluster capacity, node selectors, and tolerations.
- **An HTTPRoute isn't Accepted**: Inspect its status along with the Gateway listener's hostname, `sectionName`, and allowed route namespaces.
- **The console shows no sign-in button after Setup**: The console caches the Control Plane's configuration snapshot on startup. Restart the console after the Control Plane is Ready.
- **An agent reports that its runtime needs authentication**: The runtime didn't receive a model credential. Check the agent and organization variables, plus `daemonPool.modelCredentials` if configured for the cluster.
- **Model or Git requests from agent pods fail to connect**: The daemon pool proxies these requests on behalf of agent pods. Confirm the daemon pool has outbound HTTPS access to the provider endpoints and code hosts.
- **The console returns `401` after sign-in**: Verify that the Logto API Resource matches the Control Plane audience exactly. See [Sign-in](/self-hosting/sign-in#verify-the-setup).

For the complete value reference and a control-plane-only installation example, see the chart's [README](https://github.com/agentconnect-md/agentconnect/tree/main/charts/agentconnect).
